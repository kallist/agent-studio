# UI internationalization

## Supported locales

Agent Studio supports `en` and `zh-CN`. English is the deterministic default; browser or operating
system language is not auto-detected. The global switcher in the Studio navigation changes the
current UI immediately and is usable with keyboard and screen readers.

## Architecture and persistence

The application-owned TypeScript dictionaries in `apps/web/i18n/messages` share one recursively
typed shape. `I18nProvider` exposes the current locale, `setLocale`, typed `t()` lookup, interpolation,
and locale-aware date/number formatting. Production lookup falls back to English and never renders a
raw translation key. Tests additionally compare all leaf keys.

The non-sensitive `agent-studio.locale` cookie persists the preference with `Path=/`, `SameSite=Lax`,
and a one-year maximum age. The Next.js Root Layout validates the cookie, uses the same locale for
server rendering and Provider initialization, and sets `<html lang>`. Only `en` and `zh-CN` are
accepted; invalid values fall back to English. If cookie writes are unavailable, switching still
works for the current session.

## Translation conventions

- Use semantic keys such as `agents.new` or `runs.terminationReasons.timeout`.
- Reuse `common` actions, states, counts, loading copy, and error chrome.
- Keep English wording aligned with the v1 UI unless correcting a clear inconsistency.
- Use consistent Chinese terms: 智能体, 运行, 调试台, 知识库, 记忆, 评测, 可观测性, 工具, 引用来源.
- Use `{name}` and `{count}` interpolation instead of assembling translated sentences.
- Do not put HTML in messages or render translations with `dangerouslySetInnerHTML`.

## Localized and non-localized data

Application chrome is localized: navigation, page headings, forms, actions, validation, dialogs,
toasts, loading/empty/error states, status labels, known event labels, and dates. Canonical status,
termination, ingestion, and Evaluation values are translated only at the display boundary.

Locale never changes or translates Agent names/instructions, user prompts, model output, tool
input/output, RAG queries/documents/chunks/citations, Memory content, Evaluation inputs/expected or
actual values, provider/model identifiers, raw JSON, raw RunEvent types, API request bodies,
PostgreSQL values, or schema.

## Adding copy or a locale

1. Add an English key to `apps/web/i18n/messages/en.ts`.
2. Add the identical key to `apps/web/i18n/messages/zh-CN.ts`.
3. Use `t("namespace.key")`; do not add locale ternaries in components.
4. Run `pnpm --dir apps/web typecheck`, `test:run`, `lint`, and the i18n Playwright tests.

Adding a third locale also requires an explicit product decision, a dictionary, config registration,
switcher option, terminology review, and the same browser coverage. URL locale routes, automatic
translation, backend localization, user-account preferences, RTL, multilingual RAG, and multilingual
embedding redesign are not implemented.
